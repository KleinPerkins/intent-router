## 1. Successor rule and narrow scope

Accepted design v3 remains the active design while this file is Draft. If v4 is accepted, every v3
decision, boundary, future phase, and non-goal carries forward by reference except the narrow G0-V
sequencing amendment in this document. In particular, v4 does not copy or reopen v3's registration,
proposal, feedback, provider, privacy, calibration, resilience, fleet, migration, or future-roadmap
design.

This amendment introduces one label:

**G0-V-Q — sandbox qualification** is the plan-specific prerequisite that diagnoses the failed
G0-V-R runnerless job and selects one of two permitted continuation routes: healthy completion
within the existing profile (Route A), or qualified reuse of one existing cataloged profile
(Route B). It is not a reusable platform, a product phase, a new `status.yml` entry, or a new
router contract. Accepted artifacts and existing pull requests are not renamed.

The original v3 order remains otherwise unchanged:

```text
G0-V-Q → finish G0-V-R → G0-V-H → G0-V-P → G0-V-L
```

G0-C-AWA may remain independently owned and sequenced as v3 specifies. Final G0-R still waits for
the completed G0-V and G0-C-AWA evidence required by v3.

## 2. Observed blocker, not inferred root cause

The following are dated observations, not receipts or completion claims:

- On 2026-09-04, [PR #58](https://github.com/KleinPerkins/intent-router/pull/58) was open, Draft,
  unarmed, and mergeable. Its observed head was
  `aa0cc15c4d4b9b73288cd7c6a9af73dcb816f8b1`.
- Its exact changed paths were `Makefile`, `install.sh`, and
  `tests/test_authority_honesty.py`.
- Its recorded local gate was green in roughly 151 seconds.
- Required CheckRun `100931502200`,
  `pr-automation / job:repo.intent-router.m3-verify`, was emitted by verifier App `4274739` for
  that exact head and concluded `action_required`.
- Controller observations recorded two attempts reaching the selected profile's 300-second sandbox
  ceiling without a normal exit or captured stdout/stderr.
- The protected recipe still supplies the unchanged command
  `["run-literal", "bash", "tests/run-tests.sh"]`; the current generated lock selects
  `stdlib-shell.v1` and materializes its 300-second limit.

Local success proves the implementation can complete locally. Two sandbox timeouts prove that the
current exact controller path did not complete within its bound. Neither proves that a larger

leak, output handling defect, or controller defect could produce the same symptom.

Current controller policy rejects/skips Draft PRs during discovery and dispatch. The historical
CheckRun is an observation; new required Checks cannot serve as pre-Ready qualification.

## 3. Boundaries that remain binding

- The router proposes only and never executes or authorizes (CR1/CR2).
- Consumer kernels decide and execute and remain safe with the router absent (KI1). No capacity
  change may put the router in a consumer safety path.
- Frozen v1 contracts remain additive-only (CR4). This amendment changes no contract or additive
  manifest.
- Repository, request, catalog, and transcript content remain data, never instructions (CR5).
- Zero-link remains mandatory.
- No paid, GitHub-hosted, or self-hosted Actions runner is introduced.
- Intent-router cannot authorize or mutate the controller repository, the Dev control plane, or
  the protected host. Each owner uses its own accepted plan and authority.
- Recipe argv, command, dependency graph, required Checks, coverage mode, and rulesets remain
  unchanged.
- `.github/pr-automation.lock.json` is generated by the qualified compiler from merged authorities;
  it is never hand-edited.

These are binding repository/design constraints. The additional sequencing and evidence stops below
are plan-specific safeguards for this G0-V-Q/G0-V-R recovery.

## 5. Diagnostic-first decision

### 5.1 Exact diagnostic boundary

The controller owner must diagnose before proposing a capacity change. The diagnostic must use the
controller's real sandbox execution path with:

- the unchanged command `["run-literal", "bash", "tests/run-tests.sh"]`;
- PR #58 head `aa0cc15c4d4b9b73288cd7c6a9af73dcb816f8b1`, or one explicitly recorded refreshed descendant
  head if the implementation branch has legitimately advanced;
- the exact source tree/bundle for that head;
- the selected image, tool inventory, network policy, user, read-only root, and
  `tmpfs,noexec,nosuid,nodev` work mount;
- the current CPU, memory, pid, disk, inode, and output limits; and
- the exact controller release, live config generation, assignment, profile, recipe, and generated
  lock identities.

The diagnostic may extend an observation deadline outside live PR admission only under the
controller owner's accepted diagnostic plan. It must not change the production assignment, target
lock, PR posture, or command. A host-shell replay or a different container is not exact-sandbox
evidence.

For each attempt, retain ordinary bounded evidence:

- head/tree and all controller/profile/config/assignment/lock identities above;
- start, finish, and elapsed time;
- last completed harness stage or test when observable, otherwise an explicit `unavailable`;
- normal exit code and success marker, or precise timeout/stall/error disposition;
- bounded stdout/stderr capture, byte counts, truncation state, and available digests;
- observed resource-limit violations and cleanup/residue result; and
- whether a second unchanged run reproduced the result.

A capacity conclusion requires at least two unchanged diagnostic runs. If the first run establishes
a deterministic defect, stop and fix that defect rather than spending a second run merely to
justify more time.

### 5.2 Decision table

| Diagnostic result | Required response |
|---|---|
| **Route A — no capacity:** after any separately governed defect fix, the command repeatedly completes healthily within 300 seconds in the exact sandbox | Keep `stdlib-shell.v1`. Skip every Dev assignment, lock, activation, and capacity task; continue to PR #58's Draft audit and pre-Ready proof. |
| Command hangs, stops making progress pathologically, leaks processes/resources, or fails cleanup | Fix the defect in the owning repository through its governed plan/PR path; do not increase timeout. Re-run diagnosis from a clean exact head. |
| **Route B — capacity:** the command repeatedly completes normally beyond 300 seconds with no other limit or pathological stall | Consider only qualified reuse of the already-cataloged `awa-authoritative-verify.v1` under §6. |
| Another resource limit is causal, evidence is contradictory, or stage/stream identity is insufficient | Stop for a successor owner decision; do not hide the problem inside a broader profile. |

Any router-source fix stays on PR #58 and within its exact three-file contract. A needed fourth
router path is a stop condition. Any controller defect, diagnostic instrumentation, catalog change,
or release belongs to a separately accepted controller plan. Any Dev assignment/lifecycle change
belongs to a separately accepted Dev plan.

## 6. Route B is catalog-stable

Every generated target lock includes the semantic digest of the whole execution catalog. Current
controller release discipline therefore requires a fleet-wide relock when any digest-covered
catalog, profile, or resource value changes. This lean recovery does not mutate that catalog and
does not add any profile.

Route B may reuse only the already-cataloged `awa-authoritative-verify.v1`. It is not a
timeout-only substitute. Compared with `stdlib-shell.v1`, the checked-in catalog shows all of
these differences:

| Field | `stdlib-shell.v1` | `awa-authoritative-verify.v1` |
|---|---:|---:|
| Image | `buildpack-deps@sha256:877e…` | `ghcr.io/kleinperkins/awa-authoritative-verify@sha256:b703…` |
| Tool inventory | Bash/Python/Git plus base text/file tools | Also Make, jq, rg, and coreutils; different image contract |
| Timeout | 300 seconds | 7,200 seconds |
| CPU | 1,000 millicores | 2,000 millicores |
| Memory | 512 MiB | 2,048 MiB |
| Pids | 64 | 512 |
| Disk | 1,024 MiB | 8,192 MiB |
| Inodes | 8,192 | 65,536 |
| Output | 65,536 bytes | 16,777,216 bytes |

Network and dependency method match, but the full profile does not. Its 7,200 seconds are a
ceiling, not a measured need. Route B may proceed only if:

1. the operator explicitly accepts the complete image, tool, timeout, CPU, memory, pid, disk,
   inode, and output delta;
2. exact-sandbox qualification proves the unchanged command completes healthily under that exact
   existing profile;
3. every unchanged outer controller deadline accommodates the selected profile; and
4. no catalog/profile/resource bytes or semantic catalog digest change.

If the broad profile is rejected or unsuitable, stop. Designing a new profile requires separate
controller architecture, fleet-wide relock planning, and successor authority outside this lean
delivery.

## 7. Owner-serialized qualification and activation

Route A skips this section completely.

Route B requires a separately accepted Dev-owner plan. Current generic assignment `sync` is not a
valid reprofile path because it stages new assignments as `manual_only`; generic transcription is
also not valid for an existing required-check assignment. The Dev plan must identify—or add and
test—a narrow existing-assignment reprofile path that:

- changes only intent-router's profile reference to the existing cataloged
  `awa-authoritative-verify.v1`;
- preserves `local` coverage, both required Checks, and every non-profile assignment field;
- declares exact owner-repository and generated-target changed-path allowlists; and
- defines the exact serial publication, requiredness activation, recovery, and rollback order.

Only after that path is proven may Route B proceed:

1. Confirm the execution catalog and its semantic digest are unchanged.
2. Make the one semantic Dev assignment change and generate the target lock with the qualified
   compiler from merged authorities. The target PR changes exactly
   `.github/pr-automation.lock.json`; the lock is never hand-edited.
3. Retain the exact prior assignment/profile, generated lock, live config, and
   release/compiler identities as the rollback preimage.
4. Obtain the target owner's decision on the exact generated-lock head and merge it through the
   protected path.
5. Enter one serialized pause/drain window and prove there is no active, owed, or recovery work.
6. Follow the documented requiredness path—`stage-requiredness` and then
   `finalize-requiredness`—in the exact order fixed by the accepted Dev plan. Every mutation gets
   its own fresh, non-replayable operation ID and matching owner GO; a distinct recovery operation
   ID is mandatory. No operation ID is shared across mutations.
7. Run control-plane parity and live doctor, prove merged assignment/generated-lock/live-config
   parity and no residue, then resume as the accepted owner plan directs.
8. While PR #58 remains Draft, use the separately governed exact-sandbox diagnostic path—not PR
   discovery or required Check dispatch—to qualify healthy completion under the active broad
   profile. Record ordinary owner-operation evidence and every unchanged authority.

Current target policy marks `.github` protected and requires owner/admin handling, but it does not
require a separate target-lock plan. This accepted router successor, plus a fresh exact-head target
owner decision, is sufficient plan-level target authority. No separate
`g0-v-cap-l-target-lock-*` document or dependency reservation is created. These Draft bytes alone
authorize neither staging nor merge.

### Route B failure attribution and rollback proof

Every absent, stale, wrong-App, or non-success post-Ready Check returns PR #58 to Draft before
remediation or retry and requires refreshed evidence plus a new explicit Ready decision. That
alone does not trigger external rollback.

Invoke Route B rollback only when evidence implicates the broad profile, profile assignment,
generated lock, activation, capacity behavior, or live parity; live safety/parity is unhealthy; or
binding Dev/controller owner policy requires rollback. If a source or test failure is clearly
confined to PR #58 and unrelated to capacity, keep the successfully qualified healthy Route B
assignment active, fix forward within PR #58's exact three-file contract, rerun local and Bugbot
evidence, and obtain a new Ready decision. A required fourth path is a stop. If attribution is
ambiguous, keep PR #58 Draft and stop for owner diagnosis without arbitrary external mutation. If
live safety/parity is unhealthy, follow the owner rollback policy immediately.

When rollback is triggered, restore the exact prior preimage through the owner lifecycle. Keep or
return the controller to paused/drained state. Use fresh, non-replayable operation IDs and matching
owner GOs for every rollback mutation plus a distinct recovery operation ID. Generate—never
hand-edit—the restored lock, obtain the target owner's exact-head decision, and follow the accepted
Dev plan's reverse requiredness/publication order.

Rollback is complete only when generated-lock parity, assignment/profile/live-config parity,
control-plane verification, live doctor, no residue, and no active/owed/recovery work are all
proven and retained with the ordinary operation evidence. PR #58 stays Draft and blocked.
`stdlib-shell.v1` need not make PR #58 pass; that 300-second ceiling may be the reason Route B was
needed. An optional known-good workload that completes within 300 seconds may smoke-test controller
health, but it is not PR #58 completion evidence.

Because qualification and required Checks precede any G0-V-R merge or later G0-V child, no custom
lease, distributed compare-and-swap protocol, dependency manifest, atomic evidence store, or
reversal schema is needed. If existing owner policy cannot perform this bounded rollback, stop in
that owner repository.

## 8. Continue G0-V-R on either route

G0-V-R v2 governs the detailed continuation. At design level:

1. establish Route A with repeatable healthy completion under `stdlib-shell.v1`, or establish
   Route B with the accepted broad-profile delta, completed activation, and successful
   exact-sandbox qualification;
2. obtain the plan's explicit Resume authorization;
3. while PR #58 remains Draft, refresh its branch from then-live `main` with ordinary descendant
   history—no rebase, force push, replacement PR, or history rewrite;
4. preserve the exact three-file implementation compare;
5. on every new exact head, rerun the full local gate and a fresh Bugbot review;
6. present the exact head/base/compare plus Route A diagnostic evidence or Route B
   assignment/lock/activation/qualification evidence for explicit Ready authorization;
7. only after that decision, mark the exact head Ready so the controller can emit both required
   exact-head Checks; Draft PRs are skipped and cannot supply this proof;
8. treat those Checks as the production canary and merge gate. If either is absent, stale,
   wrong-App, non-success, or inconsistent with capacity evidence, return the PR to Draft before
   retry, attribute the failure under §7, remediate through the correct owner, refresh all
   evidence, and obtain a new explicit Ready decision even when the head SHA is unchanged; and
9. let the reviewer App exclusively own approval and native auto-merge arming; never use admin
   merge or manually arm auto-merge.

The reviewer App may merge immediately after both Checks succeed. No manual pause between green
Checks and governed merge is required or assumed. If merge precedes a separate observation step,
capture and validate the final exact-head CheckRun and merge evidence afterward.

After merge, record the merge SHA and independently verify that `merge^1` equals the exact base
recorded immediately before merge. A mismatch prevents a successful G0-V-R claim and requires an
authority-owned forward fix. This narrow first-parent rule is the only retained response to the
former receipt base-parent finding.

## 9. Evidence and rollback

No new receipt namespace or serialization contract is introduced. The durable evidence is:

- prospective accepted v4/v2 SHA-256 digests, matching post-transformation digests, exact staged
  three-path acceptance diff, doc-warden successor results, and acceptance merge;
- accepted controller/Dev owner-plan digests and merge commits;
- controller/Dev implementation PRs and merge commits, when applicable;
- Route A or Route B diagnostic attempt identities and bounded results;
- for Route B only, each distinct forward/recovery/rollback operation ID and owner GO, ordinary
  lifecycle evidence, retained preimage, and no-work/no-residue proof;
- for Route B only, before/after profile, assignment, generated-lock, live-config, controller
  release, compiler, and unchanged catalog digests;
- for Route B only, capacity-lock PR base/head/compare/Checks/merge and exact-sandbox
  qualification;
- PR #58 final base/head/compare and exact changed paths;
- exact-head local verification and Bugbot result;
- both required final CheckRun IDs, App identity, head SHAs, and conclusions;
- PR #58 merge SHA and independent `merge^1 == recorded base` result; and
- Route B rollback PRs, operations, parity, doctor, and residue/work-state evidence when the
  rollback trigger above is met.

Git commits, PRs, CheckRuns, and the existing controller/Dev operation receipts are immutable or
durably addressable enough for this checkpoint. There is no post-merge Dev receipt-only PR and no
`g0-v-r-receipt/v2` artifact. This removes the merged-but-unreceipted window, receipt-reversal
schema gap, publication gate, and address-member questions rather than solving them with a new
evidence system.

Before G0-V-H or another dependent child starts, a router defect may be corrected through an
ordinary router revert/forward-fix and the external owner may independently restore the prior
assignment/lock through its accepted lifecycle. After a dependent child starts, use the
owner-specific rollback order already required by v3; this amendment grants no cross-authority
rollback.

## 11. Stops and acceptance boundary

Stop G0-V-Q if diagnosis is not exact-sandbox and repeatable; the run stalls rather than completes;
the causal resource is unresolved or another limit; Route B proposes any catalog mutation or new
profile; the broad 7,200-second profile is proposed without explicit full-delta acceptance; an
outer timeout must change; the Dev reprofile path is absent or unproven; generic assignment

hand-edited; recipe, command, required Checks, coverage mode, or ruleset changes; the maintenance
operation cannot pause/drain, retain a preimage, pass doctor, or prove rollback; or any owner would
need authority from this router Draft.

Stop G0-V-R if neither Route A nor Route B is proven; PR #58's compare exceeds the exact three
paths; a refreshed head is not a descendant; local verification or Bugbot is not clean while the
PR is Draft; Ready lacks the exact route/head/base/compare evidence; or delivery would require
admin merge, manual auto-merge arming, force, history rewrite, or a paid runner. After Ready, an
absent, wrong-App, stale, non-success, or route-inconsistent required Check forces Draft posture,
failure attribution, owner remediation, refreshed evidence, and a new Ready decision before retry.
Stop for owner diagnosis when attribution is ambiguous; do not mutate external state arbitrarily.
A clear three-file router source/test failure fixes forward without Route B rollback. Unhealthy
live safety/parity follows binding owner rollback policy immediately.
